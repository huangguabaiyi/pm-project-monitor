# 需求进展监控工具改版设计

## 1. 设计目标

本次改版围绕“只关注当前进展、关键测试门禁和最终合板风险”收敛模型，避免把需求维护成完整项目管理看板。

目标包括：

- 让需求名称与季度 OKR 目标的含义清晰分离。
- 支持需求文档、Meego 和多语言翻译链接，并在卡片中提供入口。
- 支持一个进展节点由多个负责人共同负责，并对所有负责人发送真实 @。
- 只校验需求当前正在进行的环节，不因历史或未来环节缺失产生整流程误报。
- 只保留 AT1、AT2、PV1、PV2 和线上回归的关键最低时长配置。
- 用明确的 AT/PV/线上回归门禁判断能否继续推进和最终合板。
- 允许提前将不适用的测试轮次标记为“已跳过”。
- 使用带表头的结构化飞书卡片矩阵展示并行交付域，避免伪表格换行错位。
- 按自然日维护日期；未填写具体时间时统一按本地日期的 00:00 处理。

## 2. 范围与非目标

### 2.1 本次范围

- 需求主表字段重命名和链接字段扩展。
- 进展节点表多人负责人和跳过节点语义。
- 基础配置表新增流程环节。
- 项目级关键测试时长配置。
- 当前环节校验和 AT/PV/线上回归合板门禁。
- 日报和严重风险卡片的结构化展示。
- 日期解析、链接校验、数据迁移和回归测试。

### 2.2 非目标

- 不新增完整的任务依赖、资源负载、工时分解或验收看板。
- 不为每一个普通流程环节新增独立的复杂时间配置。
- 不通过 Webhook 接收上行指令。
- 不改变 LLM 作为可选增强器的定位；基础规则和推送不能依赖 LLM。

## 3. 数据模型设计

### 3.1 需求主表

保留一条需求一行的结构。

| 现有/新字段 | 设计含义 | 约束 |
| --- | --- | --- |
| 需求编号 | 需求唯一标识 | 必填 |
| 需求名称 | 具体需求名称，例如“3.0日志开发” | 必填 |
| OKR目标 | 由现有“项目名称”重命名而来，表示季度 OKR 目标 | 必填，允许手动填写，例如“2026年Q2 KR3” |
| 目标版本 | 需求预计进入的版本 | 可选；保留现有字段，卡片有值时展示 |
| 项目配置关联 | 需求使用的排期规则配置 | 可选；不再把它当作 OKR 目标名称 |
| 需求文档链接 | 需求文档 URL | 可选；填写时必须是 `http` 或 `https` |
| Meego链接 | Meego URL | 可选；填写时必须是 `http` 或 `https` |
| 多语言翻译链接 | 翻译任务或文档 URL | 可选；填写时必须是 `http` 或 `https` |
| 当前环节 | 当前正在推进的流程环节 | 必填；通用缺失校验只使用此字段 |
| 合板时间 | 统一合板日期 | 必填，按自然日解析 |
| 计划上线时间 | 计划上线日期 | 可选；服务端上线默认读取此字段 |
| 需求宣讲是否完成 | 是否进入可通知状态 | 必填 |
| 是否允许通知 | 需求通知开关 | 必填 |
| 是否归档 | 历史需求归档开关 | 必填 |

“需求名称”和“OKR目标”相同时，卡片只展示一次，避免重复信息。

为兼容现有表格，物理字段迁移应支持旧字段名“项目名称”的识别；迁移完成后，面向用户的字段名称统一使用“OKR目标”。

### 3.2 进展节点表

每个真实交付节点一行。研发、测试、联调和发布仍通过“交付域 + 工作类型 + 节点名称”表达配套关系；同一交付域的研发和测试是两条独立节点链路，分别维护负责人和排期。例如服务端研发对应服务端测试，客户端研发对应客户端测试，车辆研发对应车辆测试。AT/PV 测试节点按测试交付域分别建立，因此各端可以有不同的测试排期，但共同受同一个合板日期约束。

| 字段 | 设计含义 | 约束 |
| --- | --- | --- |
| 节点名称 | 流程环节或自定义节点 | 必填 |
| 关联需求 | 所属需求 | 必填 |
| 交付域 | 客户端、服务端、车辆等 | 必填 |
| 工作类型 | 研发、测试、联调、发布等 | 必填 |
| 负责人 | 共同负责该节点的人员 | 至少 1 人，可多选 |
| 计划开始时间 | 节点计划开始日期 | 普通节点建议填写；测试节点用于门禁判断 |
| 计划完成时间 | 节点计划完成日期 | 未跳过节点必填；服务端上线允许系统默认或手动覆盖 |
| 实际完成时间 | 实际完成日期 | 节点完成时填写 |
| 当前状态 | 未开始、进行中、已完成、已跳过、已取消 | 必填 |
| 进展说明 | 进展、跳过原因或处理说明 | 建议填写 |
| 最后更新时间 | 最近一次进展更新时间 | 系统字段或可兼容自动修改时间 |
| 最晚安全DDL | 系统计算结果 | 机器人回写 |
| 系统风险等级/原因 | 系统计算结果 | 机器人回写 |

多人负责人规则：

- 普通进度通知 @ 所有节点负责人。
- 严重风险通知 @ 所有节点负责人和需求项目负责人。
- 所有人名相关内容都必须使用真实飞书 @ 标签，不得把姓名作为普通文本拼接。

跳过节点规则：

- AT1、AT2、PV1、PV2 可以提前创建并设置为“已跳过”。
- “已跳过”和“已完成”都视为通过。
- “已跳过”节点不参与最低测试时长和延期计算。
- 跳过节点允许计划开始/完成时间为空；进展说明建议填写跳过原因。
- 没有创建节点且没有显式标记“已跳过”时，仍视为未配置。

### 3.3 基础配置表

基础配置表继续使用“配置名称、配置类型、排序、是否启用、备注”结构。

默认流程环节调整为：

1. 需求撰写
2. 内部评审
3. 产品需求评审
4. 设计稿输出
5. 设计宣讲
6. 需求宣讲
7. 工作量评估排期
8. 各端开发
9. 联调
10. 提测
11. AT 测试第一轮
12. AT 测试第二轮
13. PV 测试第一轮
14. PV 测试第二轮
15. 服务端上线
16. 线上回归
17. 多语言翻译
18. 版本合入

“多语言翻译”只出现一次，固定在“线上回归”之后、“版本合入”之前。

“服务端上线”只对服务端发布节点有实际意义；其他交付域不需要为了该环节创建节点。旧的“上线 Checklist”作为兼容别名读取，迁移后以“服务端上线”为唯一规范环节，不能为同一服务端上线动作生成两条节点或两次风险。

### 3.4 项目配置表

项目配置表不再保留无法和具体关键测试环节对应的专项天数配置。有效的项目级覆盖字段为：

| 字段 | 说明 |
| --- | --- |
| AT 第一轮最少测试天数 | 项目对 AT1 的最低时长覆盖 |
| AT 第二轮最少测试天数 | 项目对 AT2 的最低时长覆盖 |
| PV 第一轮最少测试天数 | 项目对 PV1 的最低时长覆盖 |
| PV 第二轮最少测试天数 | 项目对 PV2 的最低时长覆盖 |
| 线上回归最少天数 | 项目对线上回归的最低时长覆盖 |

以上字段全部允许为空。固定业务规则文档中的默认值必须按这 5 个关键节点分别提供；不再把一个 AT/PV 汇总天数或某个角色专项天数直接套用到所有轮次。计算优先级为：

`项目配置值 > 固定业务规则默认值`

节点表中的计划开始/完成日期表示当前项目的实际排期，项目配置只用于最低测试周期和风险判断，不替代节点 DDL。

## 4. 流程与规则设计

### 4.1 当前环节校验

需求主表的“当前环节”是通用流程校验的唯一入口：

- 只校验当前正在进行的环节。
- 历史环节缺失不产生整流程错误。
- 未来环节未创建不产生整流程错误。
- 当前环节没有对应节点时，生成 Warning，隔离当前需求但不停止整次运行。
- 当前环节存在多个交付域或多个负责人时，分别计算并展示。

测试门禁是独立的确定性规则，不等同于全流程缺失校验。

### 4.2 测试交付域识别

一个交付域只要为该需求创建了至少一个 `工作类型=测试` 的节点，就视为参与测试链路。

- 没有任何测试节点的纯研发交付域不纳入 AT/PV 门禁。
- 已开始维护测试节点的交付域，默认要求 AT1、AT2、PV1、PV2 链路完整。
- 某一轮显式标记“已跳过”时，该轮视为通过且不参与时长计算。
- 测试链路缺少节点或计划开始时间时，风险原因必须指出具体交付域和具体环节。

### 4.3 测试通过定义

| 当前状态 | 是否通过 |
| --- | --- |
| 已完成 | 是 |
| 已跳过 | 是 |
| 未开始 | 否 |
| 进行中 | 否 |
| 已取消 | 否 |

不新增“测试结果”字段，继续使用现有状态字段，降低维护成本。

### 4.4 测试与合板门禁

#### 进入 PV 前

当需求主表“当前环节”进入 `PV 测试第一轮`、`PV 测试第二轮` 或后续环节时，对所有参与测试的交付域检查：

- AT1 已完成或已跳过。
- AT2 已完成或已跳过。

任一条件不满足，生成严重风险，并指出具体交付域和未通过环节。

#### 服务端上线前

当需求涉及服务端并进入 `服务端上线` 或后续环节时，对所有参与测试的交付域检查：

- PV1 已完成或已跳过。
- PV2 已完成或已跳过。

如果需求不涉及服务端，则在进入 `线上回归` 或后续环节时执行相同 PV 门禁。

#### 版本合入前

当当前环节为 `版本合入` 时检查线上回归：

- 线上回归已完成或已跳过：通过。
- 线上回归未开始、进行中、已取消或未配置：生成严重风险。

#### 多语言翻译

- 多语言翻译位于线上回归之后、版本合入之前。
- 当前环节为版本合入且多语言翻译未完成/未跳过时，发送 Warning。
- 多语言翻译不参与严重风险计算。
- 多语言翻译不阻塞版本合入。
- 多语言翻译完成后不再产生该 Warning。

### 4.5 服务端上线时间

- 服务端上线节点默认读取需求主表的 `计划上线时间`作为计划完成日期。
- 如果节点表手动填写计划完成日期，以节点表值为准。
- 服务端上线日期继续校验固定业务规则中的星期和截止时间。
- 上线 Checklist 与服务端上线节点的关系在迁移时保持兼容；不应同时对同一上线动作产生重复严重风险。

### 4.6 日期语义

- 时区固定为 `Asia/Shanghai`。
- 业务维护按自然日进行。
- 只填写日期、不填写时间时，内部统一使用当天 `00:00`。
- 计划开始日和计划完成日按完整自然日参与计算。
- 卡片只显示 `YYYY-MM-DD`，不显示 `00:00`。
- 系统修改时间、日志时间可以保留实际时分秒，但不作为业务 DDL 展示。

## 5. 卡片展示设计

### 5.1 技术形式

继续通过 Webhook 发送飞书交互式卡片，但从“竖线拼接 Markdown”升级为结构化卡片布局。

程序动态生成卡片中的表头、数据行和链接入口；不依赖横向文本对齐。

### 5.2 整体需求日报

卡片组成：

1. 卡片标题：日期、日报类型和风险统计。
2. 需求摘要区：
   - 需求名称。
   - OKR目标。
   - 目标版本（有值时展示）。
   - 合板日期。
   - 计划上线日期。
   - 当前环节。
   - 当前风险等级。
3. 链接区：只展示已填写的 `需求文档`、`Meego`、`多语言翻译`入口。
4. 当前环节交付矩阵，固定表头：

   ```text
   环节｜交付域｜负责人｜计划开始｜计划完成｜最晚安全DDL｜状态
   ```

5. 风险/阻塞摘要区：只展示当前需求需要处理的内容。

每条矩阵数据行都必须包含环节列。并行交付域各占一行；多名负责人在负责人单元格内全部真实 @。

### 5.3 严重风险卡片

严重卡片只展示：

- 项目负责人严重风险提示。
- 需求名称、OKR目标、目标版本。
- 合板日期、预计完成日期、延期天数。
- 已填写的三个链接。
- 当前风险原因和处理动作。
- 当前风险相关的交付矩阵。
- 节点负责人和项目负责人。

不展开历史已完成环节，不展示与当前风险无关的普通节点。

### 5.4 卡片截断与降级

发送前进行本地结构校验和大小限制检查：

1. 完整结构化互动卡片。
2. 保留摘要、风险、链接和当前环节矩阵的精简卡片。
3. 纯文本降级消息。

单条节点过长时优先截断非关键进展说明，不得截断环节、交付域、负责人、DDL、状态和风险等级。

## 6. 链接与数据校验

链接字段规则：

- 空值合法，不展示，不报错。
- 非空值必须是 `http://` 或 `https://` 开头的 URL。
- 格式错误生成字段级数据异常。
- 只隔离当前需求，其他需求继续运行。
- 卡片按钮文本固定为“需求文档”“Meego”“多语言翻译”。

其他校验规则：

- 多人负责人字段至少包含 1 个有效飞书人员。
- 已跳过节点允许计划日期为空。
- 非跳过、非完成节点的计划完成日期仍按节点表规则校验。
- 当前环节无节点是 Warning，不升级为关键表结构错误。
- 需求宣讲未完成的需求不发送普通或严重通知。
- 已归档需求不发送通知。

## 7. 迁移策略

### 7.1 字段迁移

- 将需求主表面向用户的“项目名称”改名为“OKR目标”。
- 读取器在迁移期间同时兼容旧字段名“项目名称”和新字段名“OKR目标”。
- 新增三个 URL 字段时，已有需求默认为空。
- 现有项目配置关联记录保留，文档和界面说明改为“排期规则配置”。

### 7.2 配置迁移

- 基础配置表新增并启用“服务端上线”和“多语言翻译”。
- 重新计算两者排序：服务端上线位于 PV2 后、线上回归前；多语言翻译位于线上回归后、版本合入前。
- 项目配置表增加 AT1、AT2、PV1、PV2、线上回归 5 个可空字段。
- 旧的 `AT 最少测试天数`、`PV 最少测试天数` 等汇总配置需要迁移为默认值或标记为兼容读取，避免同一项目同时存在两套有效配置。
- 客户端专项测试天数、车辆专项测试天数等不再参与新规则计算；迁移期间只保留历史数据，不新增使用场景。

### 7.3 数据兼容

- 旧的单人负责人记录继续读取为单人列表。
- 现有 `已完成` 节点继续视为通过。
- 现有未完成测试节点不自动标记为跳过。
- 旧的“上线 Checklist”记录继续读取；迁移逻辑必须避免和新的“服务端上线”重复计时或重复告警。

## 8. LLM、推送与异常处理

- 固定业务规则文件仍是只读输入。
- LLM 只生成摘要、风险解释和行动建议，不能改变 AT/PV/回归门禁。
- LLM Token 过期或调用失败时，基础规则、卡片生成和 Webhook 推送继续运行。
- 单条需求数据错误只隔离当前需求。
- 卡片结构校验失败时按完整卡片、精简卡片、纯文本顺序降级。
- Webhook 失败按现有重试机制执行并写本地日志。
- 不发送已归档或需求宣讲未完成的需求。

## 9. 测试与验收

### 9.1 数据与迁移测试

- 旧“项目名称”字段迁移后可作为“OKR目标”读取。
- 三个可选链接为空时正常处理。
- 有效 HTTP/HTTPS 链接生成可点击入口。
- 非法链接只隔离当前需求并生成字段级错误。
- 单人负责人和多人负责人都能正常读取。
- 跳过节点允许无计划日期。
- 新增基础配置环节排序正确。

### 9.2 规则测试

- 当前环节校验不检查历史和未来环节缺失。
- 当前环节缺节点只生成 Warning。
- 参与测试的交付域缺 AT1/AT2/PV1/PV2 时指出具体环节。
- 已完成和已跳过都通过门禁。
- AT1/AT2 未通过时进入 PV 生成严重风险。
- PV1/PV2 未通过时进入服务端上线或线上回归前生成严重风险。
- 线上回归未通过时版本合入生成严重风险。
- 多语言翻译未完成时只生成 Warning，不阻塞合版。
- 项目时长字段为空时正确继承固定规则。
- 项目时长字段有值时正确覆盖固定规则。
- 服务端上线手动 DDL 正确覆盖需求主表计划上线日期。
- 自然日和日期 00:00 语义计算正确。

### 9.3 卡片测试

- 日报卡片包含明确表头：环节、交付域、负责人、计划开始、计划完成、最晚安全DDL、状态。
- 并行交付域的每行字段保持结构化对应，不依赖竖线对齐。
- 多人负责人全部生成真实 @。
- 三个链接按填写情况展示或隐藏。
- 严重风险卡片只展示当前风险相关节点。
- 空阻塞、空行动和长文本不会造成无意义大段内容。
- 卡片超长时保留关键字段并正确降级。

### 9.4 运行与降级测试

- LLM 不可用时基础规则和推送继续运行。
- Webhook 重试和纯文本降级正常。
- 本地定时任务和手动运行结果一致。
- 需求宣讲未完成、已归档需求不发送通知。

## 10. 验收标准

1. 用户可以在需求主表手动填写 OKR目标和三个可选链接。
2. 用户可以在进展节点表为一个环节配置多个负责人。
3. 用户可以提前将不适用的 AT/PV 轮次标记为已跳过。
4. 系统只对当前环节做通用缺失校验。
5. AT/PV/线上回归门禁按已完成或已跳过判断通过。
6. 多语言翻译未完成只产生 Warning，不阻塞合版。
7. 服务端上线默认读取计划上线日期且支持节点覆盖。
8. 项目关键测试时长为空时使用默认规则，有值时使用项目覆盖。
9. 日报卡片包含带表头的结构化当前环节矩阵。
10. 所有人员姓名都以真实 @ 展示。
11. 日期卡片按自然日展示，不出现无意义的 `00:00`。
12. 单条错误、LLM 故障和卡片过长不会导致整批需求停止推送。
