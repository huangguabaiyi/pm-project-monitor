# 开发域完整测试链路与分域排期提示设计

日期：2026-08-03

## 1. 背景

当前排期引擎按交付域独立计算路径。此前为了避免平台域误报，虚拟 AT/PV 环节只对存在测试节点或配置了同名测试角色的交付域生成，导致存在平台研发节点时仍只预留线上回归，平台开发的最晚安全 DDL 被计算为 2026-08-26。

业务规则现已确认：**所有存在研发节点的交付域，都必须具备完整测试链路。**

## 2. 测试链路识别规则

以下任一条件成立时，交付域视为需要测试：

1. 存在 `工作类型=研发` 的节点；
2. 存在 `工作类型=测试` 的节点；
3. 基础配置中启用了与交付域同名的测试角色；
4. 项目没有任何节点时，继续使用“项目排期”虚拟路径进行兜底计算。

需要测试的交付域默认具备完整链路：

```text
AT 测试第一轮 → AT 测试第二轮 → PV 测试第一轮 → PV 测试第二轮 → 线上回归
```

基础配置中明确停用的流程环节不生成虚拟环节。

## 3. 节点与虚拟排期

- 已存在节点且填写计划完成时间：完全采用人工计划时间。
- 已存在节点但没有计划完成时间：采用项目配置时长，项目配置为空时采用固定默认时长。
- 未创建的当前或未来关键测试环节：生成只读虚拟排期。
- `已完成`、`已跳过`视为通过，剩余时长为零。
- 虚拟排期只参与预计完成、缓冲和安全 DDL 计算，不写入多维表格，不直接形成门禁失败。

## 4. 安全 DDL

安全 DDL 继续按照同一交付域的关键路径倒推：

```text
节点最晚安全 DDL = 合板时间 - 节点之后仍需执行的测试时长
```

因此，存在平台研发节点但没有平台测试节点时，平台路径仍会自动预留 AT1、AT2、PV1、PV2 和线上回归，不再只预留线上回归。

以当前“标准化三期”为例，默认剩余测试时间为：

```text
AT1 4 + AT2 4 + PV1 3 + PV2 2 + 线上回归 2 个工作日
```

平台已有 AT/PV 人工排期时使用人工时间；缺失时使用上述虚拟时长计算。

## 5. 卡片展示

“未确定排期”必须按照交付域展示，不能把所有环节和所有交付域分别合并，避免形成错误对应关系。

推荐展示：

```text
未确定排期
平台：AT 测试第一轮、AT 测试第二轮、PV 测试第一轮、PV 测试第二轮、线上回归
客户端：PV 测试第一轮、PV 测试第二轮、线上回归
服务端：PV 测试第一轮、PV 测试第二轮、线上回归
```

同一域内的环节按照项目流程顺序排列；域顺序按照首次出现顺序保持稳定。

严重风险卡和每日汇总卡使用相同的分域展示语义。其他非排期风险仍使用“环节”和“交付域”字段。

## 6. 兼容性

- 只有设计、发布、联调等节点而没有研发/测试节点的域，不自动补齐 AT/PV。
- 已有测试节点但没有研发节点的域仍参与测试链路，例如车辆域只有测试节点的情况。
- 测试角色停用时，已有测试节点按现有过滤规则处理；存在研发节点时仍按照“开发必须测试”规则补齐虚拟链路，不能通过停用测试角色绕过测试要求。
- 线上回归继续作为完整测试链路的一部分。

## 7. 验收标准

1. 平台存在研发节点且没有平台测试节点时，生成完整 AT/PV/线上回归虚拟路径。
2. 当前“标准化三期”平台开发的安全 DDL 不再是只扣除线上回归后的 2026-08-26。
3. 客户端、服务端已配置的 AT 时间继续采用人工排期，不显示为对应域的未确定排期。
4. 卡片明确展示每个交付域分别缺少哪些排期。
5. 已完成、已跳过环节不进入未确定排期列表。
6. LLM 不可用时，基础规则和卡片推送仍然正常。
7. 全量自动化测试通过，并通过测试环境真实数据 dry-run 和 Webhook 推送验证。
