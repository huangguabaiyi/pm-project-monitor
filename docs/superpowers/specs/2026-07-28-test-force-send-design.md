# 测试环境强制推送设计

## 背景

`run-once` 当前会根据本机状态文件中的项目日报日期指纹和严重风险内容指纹进行去重。即使用户删除飞书“通知记录表”的历史记录，本机 `.state/monitor.json` 仍会阻止同一天、相同内容的重复推送。这符合日常运行要求，但不利于开发调试和卡片验收。

## 目标

提供一个明确、低风险的测试命令，使用户能够在不删除本机状态、不修改线上表格数据的情况下重复发送当前卡片：

```bash
.venv/bin/requirement-monitor run-once --env test --force
```

## 行为设计

- `--force` 仅添加到 `run-once`。
- `--force` 仅允许 `test` 运行环境；与 `prod` 同时使用时，在构造 Webhook 客户端和发送消息之前拒绝运行。
- 强制运行只绕过本次运行中的项目日报去重和严重风险指纹去重。
- 强制运行不绕过需求宣讲完成、通知开关、归档状态、字段格式、风险计算和数据异常隔离。
- `--force --dry-run` 允许使用，只生成本次应发送的完整 payload，不调用 Webhook，也不写入发送状态。
- 强制发送成功后仍正常写入本机状态、需求最近通知时间和飞书通知记录，使后续普通运行继续执行正常去重。
- `start`、`restart` 和定时任务不支持 `--force`，避免长期刷屏。

## 实现方式

CLI 将 `--force` 解析为布尔参数，并在加载配置后校验当前环境必须是 `test`。`MonitorRunner.run` 接收 `force=False`，将其传入通知构建逻辑。通知构建时，`force=True` 直接忽略日报和严重风险的既有发送指纹，但不改变卡片生成、发送、写表和状态落盘流程。

## 错误与退出

- `--env prod --force` 返回清晰的配置错误和非零退出码，不调用正式 Webhook。
- 未配置测试 Webhook 时仍按现有配置错误处理。
- Webhook 发送失败仍按现有重试和失败记录处理。

## 验证

- CLI 能解析并向 Runner 传递 `--force`。
- 同一状态下连续普通运行，第二次仍为零发送。
- 同一状态下再次使用 `force=True`，日报和当前严重风险重新发送。
- `force=True` 不发送未完成需求宣讲、已归档或关闭通知的需求。
- `prod + force` 在发送前被拒绝。
- 全量测试、编译检查和 `git diff --check` 通过。
- 使用当前测试 Webhook 执行一次真实 `run-once --env test --force`，日志显示成功且不调用正式 Webhook。
